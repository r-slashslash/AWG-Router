## What's changed

- **AmneziaWG engine: the kernel module is recommended.** The kernel module encrypts inside the Linux kernel and uses several times fewer system resources than amneziawg-go, which matters most on a small VPS with many clients or in a cascade. On a new install the installer asks which engine to use when the server fits, and the module comes first (press Enter). On an installed panel a notice at the top offers it, with an **Install the module** button; the panel then offers to restart the AWG server so it moves to the module. The new **Server → AmneziaWG engine** block shows what the server runs on and which module is loaded; `sudo awg-router install-kernel` on the server does the same as the button (Ubuntu 22.04+ or Debian 12+, kernel 7.x included). Tunnels to exits follow the server, with nothing to pick. Nothing is left without a connection: if the module doesn't build, the server stays on amneziawg-go; if a kernel update leaves the module unable to load, the server comes up on amneziawg-go and the panel tells you; if the server doesn't come up on the module after two restarts, the panel switches the module off and moves the server to amneziawg-go by itself (in Telegram too). You can also switch the engine by hand in **Server → AmneziaWG engine**: the AWG server restarts and clients reconnect within seconds. When the server moves onto the module, the panel and Telegram say so, and the bot's status shows the engine. Thanks to @paris19891 (#24).

- **CPU and memory in the status line.** Next to the client count the panel now shows how loaded the server's processor and memory are. 90% and above is highlighted; hover for the load average and how much memory is in use. Instead of the container and interface names it now says **Running** or **Error**; hover for the reason, click to jump to the messages at the top.

- **The AWG server comes back by itself.** If the AmneziaWG server's interface disappears while its container keeps running — for example, the kernel killed `amneziawg-go` when memory ran out, and clients stayed offline until someone restarted it by hand — the panel now restarts the server by itself after half a minute and tells you in Telegram. In host mode the server's service is restarted the same way. To do it by hand: **Server → Restart the AWG server**.

- **Telegram: server resources.** A new checkbox in the notification settings: memory above 90% or CPU above 95% for 5 minutes, and when it is back to normal.

- **The panel over IPv6.** The panel now opens over IPv6 as well as IPv4. An IPv6 address in **Server public address** now works the way this one field is meant to: the panel opens at it, gets its Let's Encrypt certificate for it, and clients connect to it unless you pick another address in **Address in configs**. The field's hint now explains this. The certificate now covers both the server's IPv4 and IPv6 addresses, so the panel opens without a warning at either. If Let's Encrypt can't check the second one (for example, port 80 is closed over it), the certificate covers the main address. Failed sign-ins from IPv6 are counted per /64 network, so changing the address does not get around the lockout. If your server's firewall has separate rules for IPv6, open the panel port there. Thanks to @paris19891 (#20).

- **Let's Encrypt through a web server on port 80 works.** Since 1.14.0 the panel put its test file in the wrong folder, so validation through nginx, Apache or Caddy always failed with HTTP 404 and was rolled back. If port 80 on your server is taken by a web server, open **System → Domain and certificate** after the update and set up the validation again. Thanks to @xiaomiiraqly-alt (#21).

- **Exits at an IPv6 address.** In the AmneziaVPN container mode Docker gives the container no IPv6 by default, so such an exit just showed "no connection". Now it says why and what to do: turn on IPv6 in Docker (README, "Limitations") or give the exit an IPv4 address or a domain with an A record. If IPv6 in Docker is already on, nothing changes. Thanks to @paris19891 (#20).

- **A domain in client configs.** With a panel domain, the installer now asks which address client configs use: the domain keeps configs working if the server's IP changes. Answer it without a prompt with `AWGR_CLIENT_DOMAIN=yes` or `no`. The installer no longer warns that the domain points elsewhere when `PUBLIC_HOST` is a domain, and `--reconfigure` asks again (Enter keeps what you had). Saving the **Server** tab no longer turns the `.env` address into a panel setting that silently overrode `.env`. Thanks to @koo-pub (#22, #23).

- **Moving the AWG server to the host.** `awg-router reconfigure` can now move the AmneziaWG server from its Docker container to the server itself with the same keys, port and clients, so client configs keep working. The container is only stopped and kept; if something goes wrong, it is put back. Thanks to @paris19891 (#25).

- **Uninstall asks about the AWG server.** If the panel's installer put the AWG server into a container, the server's keys and clients live in `/opt/awg-router/awg-server`, and deleting the folder after `awg-router uninstall` deleted the server too. Now `awg-router uninstall` asks whether to keep the server or remove it as well and says when the folder must stay. A reinstall that finds such an empty container says so and sets it aside, so its port is free again. A server on the host is no longer taken without asking: a reinstall or `awg-router reconfigure` that finds one asks whether to keep it or install a new one instead, in a container or on the host (clients then need new configs; the old server's config is kept in a backup folder). Removing a host server with `awg-router uninstall` now also removes the programs and the service file the panel had installed. Thanks to @paris19891 (#25, #27).

- **Updates keep your `.env`.** `awg-router update` wrote `.env` anew and dropped what you had added by hand (for example `EXIT_ENGINE` or `AWG_CONTAINER`), and reset `TLS_MODE=selfsigned` and `RECONCILE_INTERVAL`. Now everything from the previous `.env` is kept.

- **No gap after the server restarts.** After the AWG server's container restarted, its network had no routing rules for a few seconds while the tunnels to exits were starting, so clients went out directly — even with the **Block** fallback. Now the rules are in place before the tunnels start. Exits also wait for the kernel module instead of starting twice, and exits with domain names no longer hold the panel up one after another when DNS doesn't answer.

- **A faster panel.** The panel keeps its connection open between refreshes and compresses what it sends: the first load is 3–4 times smaller, and refreshing with many clients is much lighter. With a thousand clients that have personal links, each refresh took the server a second and a half; now it takes a few hundredths. With very many clients the panel also refreshes less often on a slow phone, so the page stays responsive.

- **Safer against other pages of the same site.** A page on another port of your server, or on a neighbouring subdomain, could make the panel restart the AWG server or start an update. The panel now refuses such requests.

- **One client can't stop domain rules.** A client that connected to the domain rules' handler directly could make it loop on itself until domain rules stopped working for every client. Such connections are now closed at once.

- **Smaller fixes.** Restoring a backup from another server no longer brings back the old server's address when this one uses the address from `.env`: before, client configs, the panel link and the certificate got the old IP. An exit whose fallbacks lead back to itself (A → B → A) is now refused: with all of them down, clients would have been left without a connection. The certificate keeps renewing after an unexpected error instead of stopping until the panel restarts. The **Subnet** field on the **Server** tab now shows the subnet (`10.8.1.0/24`) for a server on the host too, not the server's own address `10.8.1.1/24`, which looked like a wrong subnet (thanks to @paris19891, #26). If the AWG server doesn't take a change (for example, disabling a client), the panel now keeps the previous configuration instead of showing a change that didn't happen, and a client past its date or traffic limit is switched off on the next try. A huge `vpn://` link no longer eats the server's memory. If `state.json` is damaged (for example, the power went off during a write), the panel starts from the previous copy instead of not starting at all.

Удаление сервера на хосте через `awg-router uninstall` теперь убирает и программы и служебный файл, которые ставила панель. Спасибо @paris19891 (#25, #27).

Теперь правила стоят до запуска туннелей. - **Защита от других страниц того же сайта.** Страница на другом порту вашего сервера или на соседнем поддомене могла заставить панель перезапустить сервер AWG или начать обновление. Теперь панель отклоняет такие запросы.

- **Один клиент не останавливает правила по доменам.** Клиент, подключившийся к обработчику правил по доменам напрямую, мог зациклить его на самом себе, пока правила по доменам не переставали работать у всех. Такие соединения теперь сразу закрываются.

- **Мелкие исправления.** Восстановление копии с другого сервера больше не возвращает адрес старого сервера, когда этот берёт адрес из `.env`: раньше конфиги клиентов, ссылка на панель и сертификат получали старый IP. Выход, у которого резервы по цепочке возвращаются к нему же (A → B → A), теперь не сохраняется: когда все они лежат, клиенты остались бы без связи. Поле **«Подсеть»** на вкладке **«Сервер»** теперь и у сервера на хосте показывает подсеть (`10.8.1.0/24`), а не адрес самого сервера `10.8.1.1/24`, который выглядел как неверная подсеть (спасибо @paris19891, #26). Если сервер AWG не принял изменение (например, отключение клиента), панель теперь оставляет прежнюю конфигурацию, а не показывает несостоявшееся изменение, и клиент с истёкшим сроком или исчерпанным лимитом отключается со следующей попытки. Огромная ссылка `vpn://` больше не занимает память сервера. Если `state.json` повреждён (например, пропало питание во время записи), панель запускается с предыдущей копии, а не перестаёт запускаться.

## 改动

- **AmneziaWG 引擎：推荐使用内核模块。** 内核模块在 Linux 内核中加密，占用的系统资源比 amneziawg-go 少数倍，这在客户端多的低配 VPS 或级联中尤为重要。全新安装时，如果服务器适用，安装程序会询问使用哪种引擎，模块排在第一位（直接回车即可）。已安装的面板会在顶部通知中推荐模块，并提供 **安装模块** 按钮；安装后面板会提示重启 AWG 服务器，使其改用模块。新的 **服务器 → AmneziaWG 引擎** 区块显示服务器使用的引擎和已加载的模块；在服务器上运行 `sudo awg-router install-kernel` 与按钮效果相同（Ubuntu 22.04+ 或 Debian 12+，包括 7.x 内核）。通往出口的隧道跟随服务器，无需任何选择。不会有人断线：模块编译失败时服务器继续使用 amneziawg-go；内核更新后模块无法加载时，服务器以 amneziawg-go 启动，面板会提示；服务器重启两次后仍无法在模块上启动时，面板会自动停用模块并将服务器切换到 amneziawg-go（Telegram 中也会通知）。也可以在 **服务器 → AmneziaWG 引擎** 中手动切换引擎：AWG 服务器会重启，客户端几秒内重新连接。服务器改用模块时，面板和 Telegram 会提示，机器人的状态中也会显示引擎。感谢 @paris19891（#24）。

- **状态栏显示 CPU 和内存。** 面板现在在客户端数量旁显示服务器处理器和内存的占用情况。达到 90% 及以上时会高亮显示；悬停可查看平均负载和已用内存。状态栏不再显示容器和接口名称，而是显示 **运行中** 或 **错误**；悬停可查看原因，点击可跳到顶部的消息。

- **AWG 服务器自动恢复。** 如果 AmneziaWG 服务器的接口消失而容器仍在运行（例如内存不足时内核终止了 `amneziawg-go`，客户端一直断线，直到有人手动重启），面板现在会在半分钟后自动重启服务器并通过 Telegram 通知你。主机模式下服务器服务也会以同样方式重启。手动重启：**服务器 → 重启 AWG 服务器**。

- **Telegram：服务器资源。** 通知设置中新增一个选项：内存超过 90% 或 CPU 超过 95% 持续 5 分钟，以及恢复正常时。

- **面板支持 IPv6。** 面板现在除 IPv4 外也可通过 IPv6 打开。**服务器公网地址** 中填写 IPv6 地址现在会按这个字段的本意工作：面板通过它打开，为它申请 Let's Encrypt 证书，客户端也连接到它，除非你在 **配置中的地址** 中另选地址。字段提示现在说明了这一点。证书现在同时签发给服务器的 IPv4 和 IPv6 地址，通过任一地址打开面板都不会出现警告。如果 Let's Encrypt 无法验证第二个地址（例如该地址的 80 端口被关闭），证书只签发给主地址。来自 IPv6 的登录失败按 /64 网络计数，更换地址无法绕过锁定。如果服务器防火墙对 IPv6 有单独的规则，请在其中开放面板端口。感谢 @paris19891（#20）。

- **通过 80 端口上的 Web 服务器进行 Let's Encrypt 验证现已可用。** 从 1.14.0 起，面板把验证文件放错了目录，所以通过 nginx、Apache 或 Caddy 的验证总是以 HTTP 404 失败并被回滚。如果服务器的 80 端口被 Web 服务器占用，更新后请打开 **系统 → 域名和证书**，重新设置验证。感谢 @xiaomiiraqly-alt（#21）。

- **使用 IPv6 地址的出口。** 在 AmneziaVPN 容器模式下，Docker 默认不给容器分配 IPv6，这样的出口只会显示“无连接”。现在它会说明原因和解决办法：在 Docker 中启用 IPv6（见 README“限制”一节），或为出口改用 IPv4 地址或带 A 记录的域名。如果 Docker 已启用 IPv6，则一切照旧。感谢 @paris19891（#20）。

- **客户端配置中使用域名。** 设置了面板域名时，安装程序现在会询问客户端配置使用哪个地址：使用域名时，即使服务器 IP 变化，配置也能继续使用。可通过 `AWGR_CLIENT_DOMAIN=yes` 或 `no` 直接回答。当 `PUBLIC_HOST` 是域名时，安装程序不再误报域名指向其他服务器，`--reconfigure` 会再次询问（按 Enter 保持原样）。保存 **服务器** 选项卡不再把 `.env` 中的地址变成悄悄覆盖 `.env` 的面板设置。感谢 @koo-pub（#22、#23）。

- **将 AWG 服务器迁移到主机。** `awg-router reconfigure` 现在可以把 AmneziaWG 服务器从 Docker 容器迁移到服务器本身，密钥、端口和客户端保持不变，客户端配置继续可用。容器只会被停止并保留；如果出了问题，会恢复原样。感谢 @paris19891（#25）。

- **卸载时会询问 AWG 服务器的去留。** 如果 AWG 服务器是由面板安装程序装进容器的，它的密钥和客户端位于 `/opt/awg-router/awg-server`，在 `awg-router uninstall` 之后删除该目录也会删除服务器。现在 `awg-router uninstall` 会询问保留还是一并删除服务器，并说明何时不能删除该目录。重新安装时如果发现这样的空容器，会说明情况并把它移到一边，让端口重新空出来。主机上的服务器也不再被不加询问地直接使用：重新安装或 `awg-router reconfigure` 发现它时，会询问是保留它，还是改装一个新的服务器（在容器中或主机上；之后客户端需要新配置，旧服务器的配置会保存在备份目录中）。通过 `awg-router uninstall` 删除主机上的服务器时，现在也会删除面板安装的程序和服务文件。感谢 @paris19891（#25、#27）。

- **更新时保留 `.env`。** `awg-router update` 会重新写入 `.env`，丢掉您手动添加的设置（例如 `EXIT_ENGINE` 或 `AWG_CONTAINER`），并重置 `TLS_MODE=selfsigned` 和 `RECONCILE_INTERVAL`。现在原有 `.env` 中的所有内容都会保留。

- **服务器重启后不再有空档。** AWG 服务器的容器重启后，在通往出口的隧道启动期间，它的网络中有几秒钟没有路由规则，客户端因此直连——即使备用设为 **阻止** 也是如此。现在规则会在隧道启动之前就位。出口还会等待内核模块，而不是启动两次；带域名的出口在 DNS 无响应时也不再一个接一个地拖住面板。

- **面板更快。** 面板在两次刷新之间保持连接，并压缩发送的内容：首次加载缩小到原来的三分之一到四分之一，客户端很多时刷新也轻得多。有一千个带个人链接的客户端时，每次刷新要占用服务器一秒半，现在只需百分之几秒。客户端非常多时，面板在较慢的手机上还会降低刷新频率，让页面保持流畅。

- **防范同一站点的其他页面。** 服务器其他端口上或相邻子域名上的页面，可能让面板重启 AWG 服务器或开始更新。现在面板会拒绝这类请求。

- **单个客户端无法让域名规则停摆。** 直接连接域名规则处理程序的客户端可能让它不断连接自己，直到所有客户端的域名规则都失效。现在这类连接会被立即关闭。

- **小修复。** 从另一台服务器的备份恢复时，如果本服务器使用 `.env` 中的地址，不再带回旧服务器的地址：以前客户端配置、面板链接和证书都会变成旧 IP。出口的备用沿链条又回到它自己（A → B → A）时，现在无法保存：它们全部断开时，客户端将无法连接。证书在意外错误后会继续续期，而不是在面板重启前一直停止。**服务器** 选项卡上的 **子网** 字段现在对主机上的服务器也显示子网（`10.8.1.0/24`），而不是服务器自身地址 `10.8.1.1/24`——后者看起来像是子网错了（感谢 @paris19891，#26）。如果 AWG 服务器没有接受某项更改（例如停用客户端），面板现在会保留之前的配置，而不是显示一个并未生效的更改；到期或用完流量限额的客户端会在下一次尝试时被停用。超大的 `vpn://` 链接不再占满服务器内存。如果 `state.json` 损坏（例如写入时断电），面板会从上一份副本启动，而不是无法启动。

- **پردازنده و حافظه در نوار وضعیت.** پنل اکنون کنار تعداد کلاینت‌ها نشان می‌دهد پردازنده و حافظهٔ سرور چقدر درگیرند. از <bdi>90%</bdi> به بالا رنگی می‌شود؛ راهنمای روی آن میانگین بار و مقدار حافظهٔ مصرفی را نشان می‌دهد. به‌جای نام کانتینر و رابط، نوار وضعیت اکنون **در حال کار** یا **خطا** را نشان می‌دهد؛ راهنمای روی آن علت را می‌گوید و با کلیک به پیام‌های بالای صفحه می‌روید.

- **سرور AWG خودش برمی‌گردد.** اگر رابط سرور AmneziaWG از بین برود ولی کانتینر همچنان کار کند (مثلاً هسته به دلیل کمبود حافظه `amneziawg-go` را ببندد و کلاینت‌ها تا راه‌اندازی دستی قطع بمانند)، پنل اکنون پس از نیم دقیقه خودش سرور را دوباره راه‌اندازی می‌کند و در تلگرام خبر می‌دهد. در حالت میزبان هم سرویس سرور به همین شکل دوباره راه‌اندازی می‌شود. دستی: **سرور ← راه‌اندازی دوبارهٔ سرور AWG**.

- **تلگرام: منابع سرور.** گزینهٔ تازه در تنظیمات اعلان‌ها: حافظه بیش از <bdi>90%</bdi> یا پردازنده بیش از <bdi>95%</bdi> به مدت ۵ دقیقه، و وقتی دوباره عادی شود.

- **پنل با IPv6.** پنل اکنون علاوه بر IPv4 با IPv6 هم باز می‌شود. نشانی IPv6 در **آدرس عمومی سرور** اکنون همان‌طور کار می‌کند که این یک فیلد برایش طراحی شده است: پنل با آن باز می‌شود، گواهی Let's Encrypt را برای آن می‌گیرد و کلاینت‌ها هم به آن وصل می‌شوند، مگر اینکه در **آدرس در پیکربندی‌ها** نشانی دیگری انتخاب کنید. راهنمای فیلد اکنون همین را توضیح می‌دهد. گواهی اکنون هم برای IPv4 و هم برای IPv6 سرور صادر می‌شود، پس پنل با هر دو بدون هشدار باز می‌شود. اگر Let's Encrypt نتواند نشانی دوم را بررسی کند (مثلاً درگاه 80 روی آن بسته باشد)، گواهی فقط برای نشانی اصلی است. ورودهای ناموفق از IPv6 به ازای هر شبکهٔ <bdi>/64</bdi> شمرده می‌شوند، پس با عوض کردن نشانی نمی‌توان از قفل گذشت. اگر دیوارهٔ آتش سرور برای IPv6 قانون‌های جداگانه دارد، درگاه پنل را آنجا باز کنید. سپاس از <bdi>@paris19891</bdi> (<bdi>#20</bdi>).

- **اعتبارسنجی Let's Encrypt از راه وب‌سرور روی درگاه 80 کار می‌کند.** از نسخهٔ 1.14.0 پنل فایل آزمایشی را در پوشهٔ اشتباه می‌گذاشت، برای همین اعتبارسنجی از راه nginx، Apache یا Caddy همیشه با خطای <bdi>HTTP 404</bdi> شکست می‌خورد و برگردانده می‌شد. اگر درگاه 80 سرور شما را وب‌سرور گرفته است، پس از به‌روزرسانی **سیستم ← دامنه و گواهی** را باز کنید و اعتبارسنجی را دوباره تنظیم کنید. سپاس از <bdi>@xiaomiiraqly-alt</bdi> (<bdi>#21</bdi>).

- **خروجی با نشانی IPv6.** در حالت کانتینر AmneziaVPN، Docker به‌طور پیش‌فرض به کانتینر IPv6 نمی‌دهد و چنین خروجی‌ای فقط «بدون اتصال» نشان می‌داد. اکنون علت و راه‌حل را می‌گوید: IPv6 را در Docker روشن کنید (README، بخش «محدودیت‌ها») یا برای خروجی نشانی IPv4 یا دامنه‌ای با رکورد A بدهید. اگر IPv6 در Docker از قبل روشن است، چیزی تغییر نمی‌کند. سپاس از <bdi>@paris19891</bdi> (<bdi>#20</bdi>).

- **دامنه در پیکربندی کلاینت‌ها.** اگر دامنهٔ پنل تعیین شده باشد، نصب‌کننده اکنون می‌پرسد کدام نشانی در پیکربندی کلاینت‌ها بیاید: با دامنه، اگر IP سرور عوض شود پیکربندی‌ها کار می‌کنند. بدون پرسش هم می‌توان با <bdi>`AWGR_CLIENT_DOMAIN=yes`</bdi> یا <bdi>`no`</bdi> پاسخ داد. وقتی `PUBLIC_HOST` دامنه است، نصب‌کننده دیگر به اشتباه نمی‌گوید دامنه به سرور دیگری اشاره می‌کند و <bdi>`--reconfigure`</bdi> دوباره می‌پرسد (Enter همان قبلی را نگه می‌دارد). ذخیرهٔ زبانهٔ **سرور** دیگر نشانی `.env` را به تنظیم پنل تبدیل نمی‌کند که بی‌صدا `.env` را کنار می‌گذاشت. سپاس از <bdi>@koo-pub</bdi> (<bdi>#22</bdi>، <bdi>#23</bdi>).

- **انتقال سرور AWG به میزبان.** <bdi>`awg-router reconfigure`</bdi> اکنون می‌تواند سرور AmneziaWG را با همان کلیدها، درگاه و کلاینت‌ها از کانتینر Docker به خود سرور منتقل کند، پس پیکربندی کلاینت‌ها کار می‌کنند. کانتینر فقط متوقف و نگه داشته می‌شود؛ اگر مشکلی پیش بیاید، سر جایش برمی‌گردد. سپاس از <bdi>@paris19891</bdi> (<bdi>#25</bdi>).

- **حذف دربارهٔ سرور AWG می‌پرسد.** اگر نصب‌کنندهٔ پنل سرور AWG را در کانتینر گذاشته باشد، کلیدها و کلاینت‌های آن در <bdi>`/opt/awg-router/awg-server`</bdi> است و پاک کردن پوشه پس از <bdi>`awg-router uninstall`</bdi> سرور را هم پاک می‌کرد. اکنون <bdi>`awg-router uninstall`</bdi> می‌پرسد سرور بماند یا آن هم حذف شود و می‌گوید کی نباید پوشه را پاک کرد. نصب دوباره اگر چنین کانتینر خالی‌ای پیدا کند، همین را می‌گوید و آن را کنار می‌گذارد تا درگاهش دوباره آزاد شود. سرور روی میزبان هم دیگر بی‌پرسش برداشته نمی‌شود: نصب دوباره یا <bdi>`awg-router reconfigure`</bdi> اگر آن را پیدا کند، می‌پرسد نگهش دارد یا به‌جایش سرور تازه‌ای بگذارد، در کانتینر یا روی میزبان (آن‌وقت کلاینت‌ها پیکربندی تازه می‌خواهند؛ پیکربندی سرور قبلی در پوشهٔ پشتیبان می‌ماند). حذف سرور روی میزبان با <bdi>`awg-router uninstall`</bdi> اکنون برنامه‌ها و فایل سرویسی را هم که پنل نصب کرده بود پاک می‌کند. سپاس از <bdi>@paris19891</bdi> (<bdi>#25</bdi>، <bdi>#27</bdi>).

- **به‌روزرسانی <bdi>`.env`</bdi> را نگه می‌دارد.** <bdi>`awg-router update`</bdi> فایل <bdi>`.env`</bdi> را از نو می‌نوشت و آنچه دستی افزوده بودید (مثلاً <bdi>`EXIT_ENGINE`</bdi> یا <bdi>`AWG_CONTAINER`</bdi>) از دست می‌رفت، و <bdi>`TLS_MODE=selfsigned`</bdi> و <bdi>`RECONCILE_INTERVAL`</bdi> به حالت پیش‌فرض برمی‌گشتند. اکنون همهٔ محتوای <bdi>`.env`</bdi> قبلی حفظ می‌شود.

- **بی‌وقفه پس از راه‌اندازی دوبارهٔ سرور.** پس از راه‌اندازی دوبارهٔ کانتینر سرور AWG، تا وقتی تونل‌ها به خروجی‌ها بالا می‌آمدند، شبکهٔ آن چند ثانیه هیچ قاعدهٔ مسیریابی نداشت و کلاینت‌ها مستقیم بیرون می‌رفتند — حتی با پشتیبان **مسدود**. اکنون قاعده‌ها پیش از راه‌اندازی تونل‌ها برقرارند. خروجی‌ها همچنین منتظر ماژول هسته می‌مانند و دو بار راه‌اندازی نمی‌شوند، و خروجی‌های دارای نام دامنه وقتی DNS پاسخ نمی‌دهد دیگر یکی پس از دیگری پنل را معطل نمی‌کنند.

- **پنل سریع‌تر.** پنل میان دو به‌روزرسانی اتصال را باز نگه می‌دارد و آنچه می‌فرستد را فشرده می‌کند: بارگذاری نخست <bdi>3–4</bdi> برابر کوچک‌تر است و به‌روزرسانی با کلاینت‌های زیاد بسیار سبک‌تر. با هزار کلاینت دارای لینک شخصی، هر به‌روزرسانی یک‌ونیم ثانیه از وقت سرور را می‌گرفت؛ اکنون چند صدم ثانیه. با تعداد بسیار زیاد کلاینت‌ها، پنل روی گوشی کند کمتر به‌روزرسانی می‌شود تا صفحه روان بماند.

- **ایمن در برابر صفحه‌های دیگر همان سایت.** صفحه‌ای روی درگاه دیگری از سرور شما یا روی زیردامنهٔ مجاور می‌توانست پنل را وادار کند سرور AWG را دوباره راه‌اندازی کند یا به‌روزرسانی را آغاز کند. اکنون پنل چنین درخواست‌هایی را رد می‌کند.

- **یک کلاینت نمی‌تواند قانون‌های دامنه را از کار بیندازد.** کلاینتی که مستقیم به پردازشگر قانون‌های دامنه وصل می‌شد، می‌توانست آن را در حلقه‌ای به خودش بیندازد تا قانون‌های دامنه برای همهٔ کلاینت‌ها از کار بیفتند. اکنون چنین اتصال‌هایی بی‌درنگ بسته می‌شوند.

- **اصلاح‌های کوچک.** بازگردانی نسخهٔ پشتیبان از سرور دیگر، وقتی این سرور نشانی را از `.env` می‌گیرد، دیگر نشانی سرور قدیمی را برنمی‌گرداند: پیش‌تر پیکربندی کلاینت‌ها، پیوند پنل و گواهی IP قدیمی را می‌گرفتند. خروجی‌ای که پشتیبان‌هایش در زنجیره به خودش برمی‌گردند (<bdi>A → B → A</bdi>) اکنون ذخیره نمی‌شود: وقتی همه از کار بیفتند، کلاینت‌ها بی‌اتصال می‌ماندند. گواهی پس از یک خطای غیرمنتظره همچنان تمدید می‌شود و تا راه‌اندازی دوبارهٔ پنل متوقف نمی‌ماند. فیلد **زیرشبکه** در زبانهٔ **سرور** اکنون برای سرور روی میزبان هم خود زیرشبکه (<bdi>`10.8.1.0/24`</bdi>) را نشان می‌دهد، نه نشانی خود سرور <bdi>`10.8.1.1/24`</bdi> را که شبیه زیرشبکهٔ اشتباه بود (سپاس از <bdi>@paris19891</bdi>، <bdi>#26</bdi>). اگر سرور AWG تغییری را نپذیرد (مثلاً غیرفعال کردن یک کلاینت)، پنل اکنون پیکربندی قبلی را نگه می‌دارد و تغییری را که انجام نشده نشان نمی‌دهد، و کلاینتی که مهلت یا سقف ترافیکش تمام شده در تلاش بعدی غیرفعال می‌شود. لینک بسیار بزرگ <bdi>`vpn://`</bdi> دیگر حافظهٔ سرور را نمی‌گیرد. اگر <bdi>`state.json`</bdi> آسیب ببیند (مثلاً برق هنگام نوشتن قطع شود)، پنل از نسخهٔ قبلی راه‌اندازی می‌شود و از کار نمی‌افتد.
